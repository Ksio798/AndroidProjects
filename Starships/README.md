## Описание приложения

Starships – мобильное приложение для просмотра космических кораблей из вселенной Star Wars, разработанное на языке Kotlin с использованием Jetpack Compose.

Проект продолжает приложение из домашнего задания № 4. Добавлены юнит-тесты и интеграционные тесты для проверки загрузки данных, обработки ошибок, повторных запросов, потокового поведения, хранения избранного и взаимодействия интерфейса с ViewModel.

В приложении сохранены список кораблей, поиск, переключение страниц, экран подробностей и избранное. Используются Navigation Compose, Retrofit, Hilt и Room. Обрабатываются состояния Loading, Error с кнопкой «Повторить», Empty и Success.


## Хранение данных

База Room `starships.db` содержит таблицу `favorite_starships` с полями `id`, `name`, `model`, `manufacturer` и `starshipClass`. Поле `id` является первичным ключом.

Избранные корабли сохраняются после перезапуска приложения. Список избранного доступен без интернета, а подробности корабля загружаются из API.

## Юнит-тесты

Тесты находятся в `app/src/test/java/com/example/starships/`.

### StarshipsListViewModelTest – 5 тестов

- `initialStateIsLoadingBeforeRequestRuns` – начальное состояние соответствует Loading, запрос ещё не выполнен тестовым диспетчером.
- `successfulLoadShowsShipsAndPagination` – успешная загрузка отображает корабли и правильные признаки доступности страниц.
- `failedLoadShowsError` – ошибка сети преобразуется в состояние Error с сообщением пользователю.
- `retryAfterErrorMakesNewRequestAndShowsSuccess` – повтор после ошибки действительно инициирует новый запрос и приводит к Success.
- `emptySearchResultShowsEmptyInsteadOfSuccess` – пустой результат поиска приводит к Empty, а пробелы по краям поискового запроса удаляются.

### FavoriteStarshipMappingTest – 1 тест

- `starshipIsConvertedToCorrectRoomEntity` – модель API корректно преобразуется в запись Room, включая извлечение идентификатора из URL и сохранение всех полей записи.

### StarshipsListFlowTest – 2 теста

- `retryEmitsLoadingErrorLoadingSuccessInOrder` – проверяется полная последовательность состояний при ошибке и повторе запроса.
- `newSearchCancelsOldRequestAndDoesNotEmitOldResult` – новый поиск отменяет незавершённую старую загрузку, и старый ответ не заменяет новый результат.

## Проверка Flow и StateFlow

Тесты собирают эмиссии StateFlow в список и сравнивают всю последовательность состояний, а не только конечное значение state.value.

Первый потоковый тест проверяет последовательность `Loading → Error → Loading → Success`. Дополнительно проверяется, что выполнены две попытки запроса и отсутствуют лишние эмиссии.

Второй потоковый тест проверяет полные StarshipsListState в следующем порядке:

1. Начальное состояние Loading с пустым поисковым запросом.
2. Состояние Loading с поисковым запросом `Falcon`.
3. Состояние Success с результатом нового поиска.

После завершения старого ответа список эмиссий должен остаться прежним. Отдельно проверяется, что старый запрос получил отмену, а новый запрос отправлен с параметром `Falcon`.

## Интеграционные тесты

Тесты находятся в `app/src/androidTest/java/com/example/starships/` и выполняются на эмуляторе или Android-устройстве.

### FavoritesRoomIntegrationTest – 2 теста

- `repositoryAddsReadsAndRemovesFavoriteInRoom` – настоящий FavoritesRepository добавляет запись в Room, читает её обратно, удаляет повторным переключением и удаляет отдельной операцией removeFavorite.
- `favoriteSurvivesDatabaseCloseAndReopen` – данные сохраняются в файловой базе, затем база закрывается и открывается заново; новый Repository читает ранее сохранённую запись.

### StarshipsRetryUiIntegrationTest – 1 тест

- `retryButtonMakesNewRequestAndDisplaysLoadedShip` – настоящий экран подключён к ViewModel и Repository с Fake API. Первая попытка завершается ошибкой. Нажатие кнопки «Повторить» запускает вторую попытку, отображает Millennium Falcon и убирает сообщение об ошибке.

## Нетривиальные сценарии

- Retry инициирует новую попытку запроса, что подтверждается количеством вызовов и их параметрами.
- Пустой результат приводит именно к Empty, а не к Success с пустым списком.
- Проверяется полная последовательность эмиссий после ошибки и повторной загрузки.
- Устаревший запрос отменяется и не добавляет старый результат в UI.
- Записанные данные читаются через новые экземпляры Room и Repository после закрытия базы.
- Нажатие кнопки Retry на реальном экране меняет состояние через ViewModel и Repository.

## Детерминированность тестов

- Сетевые ответы и ошибки задаются через Fake API, без доступа к настоящему серверу.
- Юнит-тесты используют MainDispatcherRule, StandardTestDispatcher и управляемый планировщик корутин.
- CompletableDeferred позволяет явно управлять моментом получения ответа в Flow-тестах.
- Thread.sleep и случайные задержки не используются.
- Тесты Room используют изолированные базы; файловая тестовая база удаляется до и после проверки.
- UI-тест использует синхронизацию Compose Test и Espresso.
- Таймауты чтения Room ограничивают время ожидания при сбое теста.
